# Фото и видео с очков AIMB S2 MAX: архитектура

Статус: **этап 0 выполнен** — протокол восстановлен декомпиляцией официального приложения, см. [aimb-protocol.md](aimb-protocol.md). Главное: Wi-Fi очков — точка доступа с SSID/паролем, которые задаёт само приложение, файлы — по FTP `192.168.10.1`; фото для ИИ очки умеют отдавать прямо по Bluetooth; живого видео у этой платформы (BK) нет.

## Что есть сейчас

| Возможность | Сейчас в приложении |
|---|---|
| События кнопок (BLE, сервис FA00 / EA01) | Есть, работает |
| Снимок для анализа | Камера **телефона** (Camera2, работает в фоне) |
| Фото и видео с камеры очков | Нет: Wi-Fi-связи с очками в приложении нет |
| Видео в реальном времени | Нет |

## Почему «точка доступа постоянно меняется» — решаемо

У таких очков обычно две связи. BLE — канал управления, он включён всегда. Wi-Fi-точку доступа очки поднимают **по команде приложения** только на время передачи файлов. Имя сети и пароль часто генерируются заново при каждом включении (иногда меняется и подсеть). Официальное приложение их не угадывает: оно **получает их по BLE** в ответ на команду «включи Wi-Fi».

Значит, задача — не «угнаться» за точкой доступа, а повторить этот обмен:
1. Отправить по BLE команду «включи Wi-Fi».
2. Прочитать из BLE-уведомления SSID и пароль (иногда и IP).
3. Подключиться именно к этой сети.
4. Брать адрес очков из шлюза этой сети, а не из захардкоженного IP.

Косвенное подтверждение — GATT-таблица очков, снятая скриптом `probe.bat`. Кроме FA00/EA01 там есть каналы для команд, через которые, скорее всего, это и происходит:

```
FA00: EA01 notify (события кнопок), EA02 write, EA05 write/read, EA06 write/read
F618: B001 notify/read, B002 write/read
3802: 4A02 notify/write/read
```

## Этап 0 — выяснить протокол (1–2 дня, робототехник)

Порядок от быстрого к надёжному:
1. **Запросить SDK у производителя.** Такие очки обычно делает ODM-платформа, и SDK для передачи медиа часто отдают по запросу. Это может сэкономить недели.
2. **Декомпилировать официальное приложение AIMB** (jadx). Искать: `WifiNetworkSpecifier`, `WifiP2pManager`, `SSID`, `rtsp://`, `http://192.168`, UUID `0000ea02` / `0000b002`.
3. **Снять журнал BLE.** Параметры разработчика → «Журнал отслеживания Bluetooth HCI», затем синхронизировать фото в официальном приложении, `adb bugreport`, открыть в Wireshark. Нужны записи в EA02/B002 прямо перед появлением Wi-Fi и уведомления с текстом SSID и пароля (обычно видны как ASCII).
4. **Снять трафик Wi-Fi.** PCAPdroid на телефоне, или подключить ноутбук к точке очков вручную и посмотреть порты (`nmap`). Нужно узнать, как запрашивается список файлов, как скачивается файл и есть ли живой поток (RTSP / HTTP-MJPEG).

Результат этапа — короткий документ: команды Wi-Fi вкл/выкл, формат ответа с SSID/паролем/IP, API списка и скачивания файлов, есть ли живое видео.

## Целевая архитектура

```
Очки ──BLE, всегда──▶ GlassesLink (Kotlin, foreground service)
        • кнопки, события «фото снято / видео остановлено»
        • команды «Wi-Fi вкл/выкл», получение SSID и пароля
Очки ──Wi-Fi, по требованию──▶ MediaSync / LiveStream (Kotlin)
        • список новых файлов → скачивание → отметка «синхронизировано»
        • живой поток (если очки умеют) → кадры 1–2 в секунду
MediaSync ──▶ локальная галерея (сразу видна в приложении)
          ──▶ очередь загрузки (WorkManager, повтор при обрыве)
          ──▶ бэкенд POST /api/v1/media
Бэкенд ──▶ подпись кадра, ключевые кадры видео, расшифровка речи
       ──▶ память ассистента («в 14:20 вы были в аптеке») ──▶ Помощник и Галерея
```

### Подключение к Wi-Fi очков на Android

- `WifiNetworkSpecifier` (Android 10+) с SSID и паролем из BLE. Телефон подключается к сети очков как к локальной сети без интернета, а интернет до бэкенда идёт через мобильную сеть. Сокеты к очкам привязываются к этой сети через `network.socketFactory`, а не ко всему процессу.
- Системное окно подтверждения подключения появляется на каждый запрос. Чтобы его не было, нужна ассоциация с очками через `CompanionDeviceManager`: для ассоциированного устройства Android 11+ может подключаться без диалога. Это нужно проверить на целевых телефонах.
- На части телефонов (Android 12+, STA+STA) домашний Wi-Fi сохраняется параллельно. На остальных он на время синхронизации отключится.
- Если очки используют Wi-Fi Direct, а не точку доступа, то вместо этого `WifiP2pManager`. Схема та же.

### Работа в фоне

- BLE-канал уже держит foreground service (`connectedDevice`). Работу в фоне уже разрешает новая версия приложения: отдельный движок Flutter, исключение из экономии батареи, право на камеру в фоне.
- Передача файлов: тип foreground service `dataSync`. На Android 15 у него лимит около 6 часов в сутки, на синхронизацию по событиям этого хватает с запасом.
- **Не держать Wi-Fi очков постоянно**: он быстро сажает батарею. Синхронизация пачками: по BLE-событию «видео остановлено» или «фото снято», раз в N минут или по зарядке. Затем Wi-Fi выключается.
- Учёт файлов: имя + размер + время. После успешной загрузки на сервер файл на очках можно удалять (настройка).

### Видео в реальном времени

- Возможно, только если прошивка очков отдаёт живой поток (RTSP, HTTP-MJPEG или свой протокол). Это проверяется на этапе 0: смотреть, есть ли в официальном приложении «просмотр в реальном времени».
- Если поток есть: на телефоне Media3 (модуль RTSP) или FFmpeg, раз в 0,5–1 с из него берётся кадр и отправляется на бэкенд по уже существующему `WSS /api/v1/ws/stream`. Модель отвечает потоком токенов, ответ озвучивается в очках.
- Гнать на сервер полное видео дорого (720p H.264 — 1,5–3 Мбит/с) и для ИИ не нужно. 1 кадр в секунду в JPEG — это 50–100 КБ/с.
- Живой режим включает пользователь явно: камера и Wi-Fi вместе разряжают очки примерно за 30–60 минут (оценка, проверить).
- Если живого потока у прошивки нет, то лучшее, что возможно, — «почти реальное время»: короткие клипы по кнопке, синхронизация сразу после остановки записи.

## Этапы

| Этап | Что получаем | Оценка |
|---|---|---|
| 0. Протокол | Команды Wi-Fi, SSID/пароль, API файлов, есть ли живой поток | 1–2 дня |
| 1. MediaSync в приложении | Фото и видео с очков в Галерее, в фоне | ~1 неделя |
| 2. Медиа на бэкенде | `/api/v1/media`: подписи, ключевые кадры, речь → память и Помощник | ~1 неделя |
| 3. Живой режим | Ассистент комментирует происходящее по потоку | 1–2 недели, если поток есть |

## Риски

- Протокол может быть зашифрован или подписан. Тогда нужен SDK производителя или более глубокий реверс.
- Агрессивные оболочки (Xiaomi, Huawei, Samsung) убивают фоновые службы. Помогают ассоциация CDM, исключение из экономии батареи и инструкция для пользователя.
- Пока идёт синхронизация, телефон должен быть рядом с очками (радиус Wi-Fi).
